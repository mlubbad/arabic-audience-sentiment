## Why
`docs/engineering/metrics.md` lists "Hours since last successful collection" as **not
monitored**. What we have today:
- **Ops page:** shows whether the worker *process* is alive (`worker_seen`, a 3-minute window).
- **Channels page:** shows each channel's *last run of any mode*: `last_sync_at` and
  `last_sync_status` from the `public.admin_channels()` lateral, which includes `discover`
  and `analyse`.

Neither answers the question that has bitten us before: **is this connected channel still
getting new comments?** A worker can be alive while one channel's collections keep failing
(quota, revoked OAuth, a provider error). Discover and analyse runs can also keep
`last_sync_at` fresh while collection is dead.

## Tasks
1. **SQL.** In a new migration, `create or replace function public.admin_channels()`. Start
   from the definition in `supabase/migrations/20261005010000_counts_from_video_comment_stats.sql`
   (WO-12) and copy it exactly. Add one key:
   - `last_collect_ok_at` = the latest `coalesce(sr.ended_at, sr.started_at)` among this
     channel's `public.sync_runs` with `mode = 'collect'` and `status in ('succeeded',
     'partial')`, or `null` if there are none. `partial` counts as success because it means
     comments were collected but the run stopped early, usually at the daily quota.
   - Use a second `left join lateral … order by sr.started_at desc limit 1` so it rides the
     existing `sync_runs_channel_started (channel_id, started_at desc)` index.
   - Everything else stays unchanged: the admin check, the existing keys and order, and the
     grants.
2. **Contract.** Add `last_collect_ok_at: timestamp.nullable()` to `AdminChannelSchema` in
   `packages/contracts/src/admin.ts`. The schema is `.strict()`, so the SQL and the
   contract must change in the same PR.
3. **UI** (`apps/web/src/admin/AdminChannelsPage.tsx`).
   - Add a column, "Last successful collection", showing the time as a relative age (for
     example "3 h" or "2 d") with the full timestamp in `title`.
   - For a channel with `status = 'connected'`, show a warning badge when
     `last_collect_ok_at` is `null` or older than **48 hours**. Put the threshold in one
     named exported constant, so the owner can change it in one place.
   - Disconnected channels get no badge.
   - Use the existing `Badge` tones. New strings are appended at the end of
     `strings/ar.ts` and `strings/en.ts`.
4. Regenerate `supabase/schema/current.sql` with the repo's tooling. `npm run
   db:snapshot:check` must pass.

## Acceptance criteria
- [ ] **SQL (DB test).** Seed one channel with `collect` runs (`failed` newest, then
  `partial`, then `succeeded` oldest) plus a newer `discover` `succeeded` run. Then:
  - `last_collect_ok_at` is the `partial` run's time;
  - `last_sync_at` is still the `discover` run's time, so nothing else changed;
  - a channel with only failed collects has `null`, and so does a channel with no runs.
- [ ] **Parity.** For the same seed, `comment_count` and `video_count` equal WO-12's values.
  The existing `admin_observability.test.ts` and `counts_from_stats.test.ts` pass unedited.
- [ ] **Contract.** `AdminChannelsSchema` parses the new SQL output, and still rejects an
  unknown extra key, because `.strict()` stays.
- [ ] **UI (component test).**
  - A connected channel collected 49 h ago shows the stale badge, and one collected 47 h
    ago does not. Use a fixed clock, never the real time.
  - A connected channel with `null` shows the badge; a disconnected one never does.
  - Both languages render the new label.
- [ ] **Mutation proof:**
  - dropping `'partial'` from the status list fails the SQL test;
  - flipping the comparison at the threshold fails the 47 h/49 h test;
  - removing the `connected` condition fails the disconnected-channel test.
- [ ] `npm run check`, `npm run test:db`, `npm run db:snapshot:check` and `npm run test:e2e`
  pass. Paste the summary lines.
- [ ] No deploy, no remote migration, never push to `main`.
