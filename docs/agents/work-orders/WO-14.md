## Part A: honest KPIs
**The problem today:**
- `apps/web/src/dashboard/Dashboard.tsx:441-443` hard-codes `replies: 0` and `unknown_dates: 0`.
- It derives `unique_authors` from `agg.people`, which the SQL caps at 10.

**What to build:**
1. **One new migration** redefines `private.dashboard_aggregates_impl(w uuid, f jsonb)`.
   - Start from its latest definition on `main`: `supabase/migrations/20261001000000_historical_import_and_dashboard_sql_correctness.sql`.
   - Add `replies`, `unknown_dates` and `unique_authors`, computed over **the same filtered row set** as `total`. The filters arrive in `f`.
   - Compute them inside the existing filtered scan. Do not add another pass over `public.comments`.
   - Keep the authorization check, `search_path=''`, fully qualified names, `statement_timeout`, and the existing revoke/grant lines exactly.
2. **Parity with the client definition.** These are the definitions in `packages/contracts/src/snapshot.ts:270-274`, used in fixture mode. The server must match them exactly:
   - `replies` = rows with `is_reply`;
   - `unknown_dates` = rows with `published_at is null`;
   - `unique_authors` = the count of **distinct non-null `author_channel_id`**. No fallback to `author_name`, and the channel owner is **not** excluded.
   - The `99ee202` draft used `coalesce(author_channel_id, author_name)` and excluded the owner. Do not copy that.
   - If you think the client definition is wrong, say so in the PR. Don't change it in this WO.
3. **Contract:** add the three fields to `DashboardAggregatesSchema` (`packages/contracts/src/fixture.ts:53`) as `z.number().int().nullable().optional()`. `.strict()` behavior, if present, stays.
4. **Client:**
   - `Dashboard.tsx` maps the three fields from `agg` and uses `null` when absent. Delete the hard-coded values.
   - `Summary.tsx` (replies and unique-authors tiles) and `Hero.tsx` (authors pill) render "—" for `null`.
   - Change only those lines in those two files: Gemini still owns the rest of them (#46 task 5).

## Part B: the live export covers every filtered row
**The problem today:** `buildExport` (`apps/web/src/data.ts:646`) reads `loadSource`, i.e. `dashboard_snapshot`. In live mode that is the most recent 1,500 comments only, so a live export silently drops everything older.

**What to build:**
1. **Live mode pages through `dashboard_comments`** with the screen's filters (`filtersToRpc(filters)`):
   - stop at `EXPORT_ROW_CAP` (10,000);
   - `totalRows` comes from the server's filtered total;
   - fixture mode keeps today's path.
2. **When the cap is hit, both the UI and the file say so.**
   - The UI toast exists already: `S.exportTruncatedNotice`, used in `Dashboard.tsx:602`.
   - The file says so in its **filename**: `…-first-10000-of-<total>.csv`. This keeps the CSV body parseable.
3. **Labels in the export:** sentiment and topic labels resolve exactly as on screen, against `active_analysis_key` / `active_topic_key` from the aggregates read.
