## Why
WO-14 (#76, PR #78) made the live CSV export read every filtered row through `dashboard_comments`. It pages with `OFFSET` (`supabase/migrations/20260924200000_optimize_dashboard_performance.sql`, `private.dashboard_comments_impl`, `LIMIT p_limit + 1 OFFSET p_offset`).

The PM review recorded two known limits:
- **Cost.** A 10,000-row export makes 100 calls. Each call re-runs the filter, sort and label CTEs, plus `count(*)` over the whole filtered set, at `OFFSET` up to 9,900. On AJ360 (~195k comments) that may take minutes.
- **Drift.** A comment inserted mid-export shifts every later offset by one, which duplicates or skips a row.

The function already returns `next_cursor` (the last row's id), but it never reads a cursor back.

## What to build
1. **One new migration** redefines `private.dashboard_comments_impl(w uuid, f jsonb)`.
   - Start from its latest definition (the file above).
   - Keep the authorization check, `search_path=''`, fully qualified names, `statement_timeout`, every filter, the output shape and the existing revoke/grant lines exactly.
2. **Keyset cursor (`f->>'after'`).** When present, page with a seek predicate instead of `OFFSET`.
   - The seek runs on the same sort tuple the query orders by, ending in `f.id DESC`, for each of the four sorts (`published_desc`, `published_asc`, `likes_desc`, `likes_asc`).
   - It must handle `NULLS LAST` correctly.
   - The cursor is an opaque text token. It encodes the sort name, the sort value(s) of the last row, and its id.
   - `next_cursor` returns a token in that format. `offset` keeps working unchanged for callers that send it, which is the dashboard's page UI today.
3. **Bad cursors:**
   - a malformed cursor;
   - a cursor minted under a different `sort`;
   - a cursor whose id is not a comment of `w`.

   All three raise `invalid_cursor` with errcode `22023` and leak nothing about other workspaces. The client already maps `invalid_cursor` (`apps/web/src/data.ts:561`).
4. **`f->>'with_total' = 'false'`** skips the `count(*)` over the filtered set; `total` is then `null`. Default behaviour (the total is counted) is unchanged. Update `DashboardCommentsResponseSchema.total` to `.nullable()` only if you use this, and keep every existing caller that reads `total` sending the default.
5. **Client export** (`buildExport` in `apps/web/src/data.ts`):
   - page 1 as today (it needs the total);
   - every later page sends `after: <previous next_cursor>` and `with_total: "false"`.

   Keep the WO-14 behaviour: cap 10,000, `-first-10000-of-<total>` filename, labels from the aggregates keys.

- [ ] **DB test, drift:** insert a newer comment between page 1 and page 2. The keyset walk returns every original row exactly once.

- [ ] **DB test, `with_total=false`:** returns `total: null` and the same rows.
- [ ] **Isolation:** workspace B's rows never appear in a walk over A.
