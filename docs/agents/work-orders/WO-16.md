## Why
The admin services page (`/admin/services`) now shows only what the server measured (PR #86, PR #87). Today that is the database and the worker. The other 13 services read `not_monitored`.

Five of them already leave records in the database every day, so their health can be read at no extra cost:
- **YouTube, Telegram, X and TikTok.** Every collection run writes a `public.sync_runs` row with `status`, `error_code`, `started_at` and `ended_at`.
- **Paddle.** Every webhook writes a `private.billing_events` row with `applied_at` and `outcome`.

This WO reads those records. It makes **no new external call** and costs no quota. Active probes (Apify, Bright Data, Auth, Edge Functions, Gemini, hosting) are phase 2 and out of scope. They need an owner decision on quota.

**Two facts the design must respect:**
1. **`sync_runs.source` is always `'unknown'`.** All three writers (`claim_job`, the two `finish_job` paths; `supabase/schema/current.sql:1609`, `:4757`, `:4808`) insert the literal `'unknown'`. The platform therefore comes from `public.channels.platform` (check: `youtube`, `telegram`, `x`, `tiktok`, `facebook`, `instagram`) joined on `(workspace_id, channel_id)`. Do not change the writers in this WO.
2. **`sync_24h.youtube_runs` is always 0 today.** It counts `source = 'youtube'` (`supabase/migrations/20261009010000_restore_admin_services_health.sql:44`). Fix it to count by `channels.platform = 'youtube'`.

## What to build
1. **One new migration** that redefines `public.admin_services_health()`.
   - Start from `supabase/migrations/20261009010000_restore_admin_services_health.sql`.
   - Keep the `is_platform_admin()` check and its `forbidden`/`42501`, `stable security definer set search_path=''`, fully qualified names, and the revoke/grant lines exactly.
   - Keep every existing key (`checked_at`, `database`, `worker`, `sync_24h`, `billing`) with its current meaning, except the `youtube_runs` fix above.
2. **New key `platforms`:** one object per platform in `youtube`, `telegram`, `x`, `tiktok`. Always emit all four, even with no runs.
   - Count only runs with `mode in ('discover','collect')` and `status <> 'running'` (finished runs) that started in the last 7 days.
   - Fields:
     - `last_status`: the status of the most recent finished run, else `null`;
     - `last_finished_at`;
     - `last_success_at`: the latest `succeeded`;
     - `last_failure_at` and `last_error_code`: the latest `failed` or `blocked`;
     - `runs_24h` and `failures_24h` (`failed`, `blocked`, `partial`);
     - `consecutive_failures`: finished runs since the latest success that are `failed` or `blocked`, capped at 10.
   - `error_code` is free text from the worker (max 80 chars, e.g. `quota_exceeded`, `rate_limit_exceeded`, `apify_quota_depleted`, `retry_exhausted:<reason>`). Return it as stored. Return nothing else from the run, no channel ids and no workspace ids: the admin page needs health, not tenants.
3. **New key `billing_webhooks`:** from `private.billing_events`.
   - `last_received_at`: `max(applied_at)`, else `null`;
   - `last_outcome`: the outcome of that row;
   - `received_24h`;
   - `problems_7d`: rows with outcome `unmapped` or `conflict` in the last 7 days.
   - Return no payload, no event ids and no workspace ids.
4. **Client mapping** in `buildLiveServicesReport` (`apps/web/src/admin/adminRead.ts:127`). Extend `ServicesHealthRpc` (`:106`) with the two keys.
   - Map `youtube`→`youtube_api`, `telegram`→`telegram_api`, `x`→`x_twitter_api`, `tiktok`→`tiktok_api`.
   - Status rules, first match wins:
     - no finished run in 7 days (`last_status` null) → keep `not_monitored`; details say no run in 7 days;
     - `last_error_code` on the latest run is a quota or rate code (`quota`, `rate_limit`, `rate_limited`, `insufficient_quota` substrings, case-insensitive), or `consecutive_failures >= 3` → `down`;
     - latest run `failed`/`blocked`/`partial`, or `last_success_at` older than 48 h → `degraded`;
     - otherwise → `healthy`.
   - Set `error_code` to `last_error_code` when the status is `down` or `degraded`.
   - Details give the last success and the 24h runs/failures. Use the existing Arabic style of `pg.details`. Isolate any Latin code inside Arabic text with FSI/PDI (`⁨…⁩`); in tests, build those characters with `String.fromCodePoint`, because prettier rewrites the escapes.
   - Keep `latency_ms`, `quota_used` and `quota_total` at `null` for these services: a run record measures neither.
   - **`paddle_billing`:**
     - no event ever → `not_monitored`, details say no webhook received yet;
     - `problems_7d > 0` → `degraded`;
     - `last_received_at` within 30 days → `healthy`;
     - older → `not_monitored`, with the last received date in details.
     - Never `down`: silence is not an outage for a low-volume webhook.
   - An RPC that lacks either key (an older server) leaves those services `not_monitored`, exactly as today.
   - All other services stay as they are.

## Acceptance criteria
- [ ] **DB test, per platform:** seed channels on all four platforms (plus one `facebook` channel that must be ignored) and `sync_runs` rows that hit each state:
  - only successes;
  - latest failed after a success;
  - three failures in a row;
  - a latest `quota_exceeded`;
  - only runs older than 7 days;
  - a `running` row (must be ignored).

  Assert every field of `platforms`.
- [ ] **DB test, cross-tenant:** runs from two workspaces aggregate into one platform total. The output contains no workspace id, channel id or payload. Assert on the serialized JSON.
- [ ] **DB test, `youtube_runs`:** counts YouTube runs by platform (non-zero with seeded runs).
- [ ] **DB test, billing:** no events → `last_received_at` null; `applied`, `unmapped` and `conflict` rows give the right `received_24h`, `problems_7d` and `last_outcome`.
- [ ] **DB test, access:** a non-admin gets `forbidden`, and anon gets permission denied (copy the pattern in `supabase/tests/admin_services_health.test.ts`).
- [ ] **Unit tests** in `adminRead.test.ts`:
  - each status rule for a platform, at both 48 h and 7 d edges;
  - quota code → `down` with `error_code` set;
  - each Paddle rule;
  - an RPC without the new keys leaves all five `not_monitored`;
  - the summary counts and `overall_status` follow.
- [ ] **Mutation proof** (show each failing):
  - platform taken from `sync_runs.source` instead of `channels.platform`;
  - `running` rows counted;
  - quota code not treated as `down`;
  - Paddle `problems_7d` ignored.
- [ ] **Cost note in the PR:** `explain analyze` of the new function on a seeded workspace with ~50k `sync_runs`. Don't add an index without saying why.
- [ ] `npm run check`, `npm run test:db` and `npm run db:snapshot:check` pass. Paste the summary lines.
- [ ] No deploy, no remote migration, never push to `main`.
