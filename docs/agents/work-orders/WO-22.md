## Why
B-2 (a channel's genre profile) and B-4 (the competitor score) both need every video labelled with a genre from our taxonomy. Nothing classifies videos yet. Topics already do the same job for comments, so this work order copies that pattern: a due list, an enum-constrained Gemini call, a commit that is refused whole when malformed, and one row per item per classification key.

**Policy gate (read first).** YouTube's Developer Policies forbid inferring a video's or channel's category unless our use case is accepted under the Derived Metrics amendment (`developers.google.com/youtube/terms/derived-metrics-policy`, §3 "Content Categorization and Tagging"). The owner is applying now. So this work order ships the pipeline **switched off**: nothing is enqueued until the owner turns the switch on after acceptance. No UI shows genres in this work order.

## Tasks
1. **The switch.**
   - Add `private.platform_switches(key text primary key, enabled boolean not null default false, updated_at timestamptz not null default now(), updated_by uuid)`, seeded with `('genre_classification', false)`.
   - Add `public.admin_set_platform_switch(p_key text, p_enabled boolean)`: `is_platform_admin()` only, refuses an unknown key with `invalid_input`, and writes an `audit_events` row (`action 'platform_switch_set'`, `target_type 'platform_switch'`, `target_id` the key, `workspace_id` null). Executable by `authenticated` only.
   - Add `private.switch_on(key text) returns boolean`.
2. **The table.** `public.video_genre_predictions`, on the pattern of `topic_predictions` (`20260916010000_a_comment_has_a_topic.sql:75-96`):
   - Columns: `id`, `workspace_id`, `video_id`, `classification_key`, `taxonomy_version int`, `status` (`succeeded|skipped|failed|unsupported`), `genre_key text null`, `confidence numeric(4,3) null`, `model_id`, `prompt_version`, `error_code text null`, `predicted_at`.
   - Unique `(workspace_id, video_id, classification_key)`. FK `(workspace_id, video_id)` to `videos`. FK `(taxonomy_version, genre_key)` to `genre_taxonomy(version, key)`.
   - Check: `genre_key` is not null exactly when `status = 'succeeded'`.
   - RLS: tenant read through `private.has_role(workspace_id)`; no direct writes for `authenticated` or `anon`.
3. **The key.** `private.genre_classification_key(taxonomy_version int, model_id text, prompt_version text)` returns `'genres:v' || taxonomy_version || '+' || model_id || '+' || prompt_version`. The version is the latest in `genre_taxonomy_versions` at due time and is echoed back in the commit.
4. **New job type `genre_classify`.**
   - Add it to `JobSchema.type` in `packages/contracts/src/jobs.ts:12` and to the `jobs_type_check` constraint. Claude signs off on this contract change by issuing this work order. Change nothing else in `jobs.ts`.
   - Enqueue from `private.schedule_due_work` only when `private.switch_on('genre_classification')` is true and the channel has pending videos.
   - "Pending" means: among the channel's **50 most recent videos** by `published_at` that have a non-empty title, one with no `succeeded`/`skipped`/`unsupported` row under the current key.
   - Use `private.enqueue_scheduled(w, c, 'genre_classify')`, so the existing one-in-flight and back-off rules hold. At most one `genre_classify` job per channel per 24 hours.
5. **Due list.** `public.svc_worker_genres_due(credential_hash, j, t, model_id, prompt_version, max_rows)` wraps `private.worker_genres_due`, like `worker_topics_due` (`current.sql:6435`).
   - Job type must be `genre_classify`. `max_rows` is clamped to 1..50.
   - Returns `{classification_key, taxonomy_version, taxonomy:[{key, parent_key, level, name_en, description}], rows:[{external_video_id, title, description, tags, category_id, duration_sec}]}`.
   - `description` is cut to its first 500 characters. If the switch is off, it returns `{blocked:'genre_classification_off'}`.
6. **Commit.** `public.svc_worker_commit_genres(credential_hash, j, t, b, records)` wraps `private.worker_commit_genres`, mirroring `worker_commit_topics` (`current.sql:6086-6180`):
   - At most 50 records.
   - Every record carries the server's key and `taxonomy_version`, a known `external_video_id` in the job's channel, and, when succeeded, a `genre_key` that exists in that version. Otherwise the whole batch is refused as `invalid_batch` (invariant 4).
   - A replay of the same batch is a no-op; the same `b` with different records is `batch_conflict` (`job_batches`, as topics do).
   - Upsert: only a `failed` row is overwritten.
7. **Spend.** Not charged to plan units in this version (owner decision pending, see Notes). Each video costs at most one Gemini call per key, because of the unique constraint and the 50-recent cap. Do not add a `usage_events` kind.
8. **Gateway.** Add `/worker/genres-due` and `/worker/commit-genres` beside `/worker/topics-due` and `/worker/commit-topics` (`worker-gateway.ts:451-473`), with the same lease checks and SQLSTATE mapping.
9. **Worker.** Add `workers/python/src/genres/gemini.py`, modeled on `workers/python/src/topics/gemini.py`:
   - `PROMPT_VERSION = "g1"`, `CHUNK = 50`, `temperature 0`, `responseMimeType application/json`.
   - `responseSchema`: an array of `{index INTEGER, genre_key STRING enum=<all keys>, confidence NUMBER}`, all required.
   - The prompt is in Arabic. It lists each genre as `key — name_en — description`, indented by level. The rule: **choose the most specific genre that fits; if only a level-1 genre fits, choose it; never invent a key.** Each video is title, then description, then tags.
   - Reuse the topics error codes and retry rules, and the bisect-once on `gemini_bad_response`.
   - `run_genres` in `runner.py` follows `run_topics` (L510-578): `due`, then classify, then commit per slice, then finish. Finish `blocked` on `genre_classification_off`, `gemini_credits_depleted` or `invalid_credentials`, and `partial` on the first failed commit.
   - The claim scope adds `genre_classify` only when a genre classifier is configured (`loop.py:320-378`, a `--genres` flag defaulting to `gemini` when `GEMINI_API_KEY` is set).

## Acceptance criteria
- [ ] Each new test fails on the old code (say how you proved it)
- [ ] Switch off (the default): `schedule_due_work` enqueues no `genre_classify` job, and `genres-due` answers `blocked: genre_classification_off`. Switch on: one job per channel with pending videos, and none for a channel whose 50 recent videos all have a final row.
- [ ] `admin_set_platform_switch` refuses a non-admin and an unknown key, and writes exactly one audit row per change
- [ ] Commit refuses the whole batch for:
  - an unknown genre key, a key from another taxonomy version, or a stale classification key;
  - a video outside the job's channel;
  - a `succeeded` row without a genre, or a `failed` row with one.
- [ ] Replay is a no-op, a conflicting replay is `batch_conflict`, and a `succeeded` row is never overwritten
- [ ] Tenant isolation: workspace A cannot read B's predictions, and `authenticated` cannot insert or update directly
- [ ] Python, with every HTTP call mocked:
  - the enum in the request equals the due list's keys;
  - a bad key in the answer gives `gemini_bad_response`, then one bisect;
  - the chunk is 50;
  - `golden_genres.json` is written by the real builder, and the TS seam test commits it through PGlite.
- [ ] `npm run worker:test`, `npm run worker:lint`, `npm run check` and `npm run test:e2e` pass (paste the summary lines)
