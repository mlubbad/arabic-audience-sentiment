## Why
B-4 scores competitors, but it needs a pool of candidate channels to score. Roadmap §4.3 lists the sources. This work order builds the pool and its two cheapest sources:
- **manual:** a channel the workspace adds by hand. It costs no YouTube quota.
- **featured:** the channels a channel shows on its own page, from YouTube's `channelSections`. It costs 1 unit, plus 1 unit per 50 channels for their titles. Roadmap §4.3 calls this a strong and cheap signal.

**Not in this work order:** YouTube search (`search.list`, 100 units). It needs a platform-level job that belongs to no workspace, and no such job exists yet. It will be its own work order (B-3b) once that design is settled.

Candidates are just channel identities: an id, a title, a handle, and where each came from. They are not derived metrics, and nothing here scores them.

## Tasks
1. **The pool.** Create `public.competitor_candidates`:
   - Columns: `id`, `workspace_id`, `channel_id` (our channel, FK `(workspace_id, id)` to `channels`), `platform text default 'youtube'`, `candidate_external_id`, `title text null`, `handle text null`, `source` (`manual|featured`), `added_by uuid null` (set for manual only), `first_seen_at`, `last_seen_at`.
   - Unique `(workspace_id, channel_id, platform, candidate_external_id, source)`.
   - Check: the candidate is not the channel itself (`candidate_external_id` ≠ the channel's `external_channel_id`; enforce in the RPCs and in the commit).
   - RLS: tenant read via `private.has_role(workspace_id)`. No direct writes for `authenticated` or `anon`.
   - Validate `candidate_external_id` with the same rule `private.register_public_channel_impl` uses for a YouTube id (`current.sql:4951-5010`); reuse its check, don't copy a new regex.
2. **Manual RPCs**, each checking membership the way `register_public_channel` does (owner or editor writes; any member reads):
   - `public.competitor_candidate_add(p_channel uuid, p_external text, p_title text, p_handle text)`: upserts the `manual` row and refreshes `last_seen_at`. Refusals:
     - `invalid_input` for a bad id;
     - `invalid_candidate` for the channel itself;
     - `candidate_limit_reached` beyond **100 manual candidates per channel**;
     - `forbidden` for a viewer or a non-member.
   - `public.competitor_candidate_remove(p_channel uuid, p_external text)`: deletes the `manual` row only. A `featured` row is the source's and comes back on the next check.
   - `public.competitor_candidates(p_channel uuid)`: returns `[{candidate_external_id, title, handle, sources: [...], first_seen_at, last_seen_at}]`, one entry per candidate with its sources merged.
3. **Featured: when.**
   - Add `channels.featured_checked_at timestamptz null`.
   - `public.svc_worker_featured_due(credential_hash, j, t)` answers `{due: true|false}` for the discover job's channel. It is due when that channel is YouTube and `featured_checked_at` is null or older than **7 days**. It runs under the same lease checks as the other discover routes.
4. **Featured: fetch** (worker). In `youtube_api.py` add `featured_channels(external_channel_id) -> list[dict]`:
   1. Call `channelSections.list(part=contentDetails, channelId=…)`.
   2. Collect `contentDetails.channels` from every section and de-duplicate them, keeping first-seen order. Cap at 100, and drop the channel itself.
   3. Call `channels.list(part=snippet, id=<≤50 ids>)` per 50 ids for `title` and `customUrl` (the handle).
   - Missing fields are `None`, never `""`. Mock every HTTP call in tests. Units: 1 + ⌈n/50⌉.
5. **Featured: commit.** `public.svc_worker_commit_featured(credential_hash, j, t, b, candidates)`:
   - At most 100 candidates per call.
   - Each needs a valid id, is not the channel itself, has a title and handle of at most 200 characters, and appears once. A bad batch is refused whole as `invalid_batch` (invariant 4). Replay is a no-op; a conflicting replay is `batch_conflict` (`job_batches`, as `worker_commit_topics` does at `current.sql:6136-6141`).
   - It upserts the `featured` rows, refreshing `title`, `handle` and `last_seen_at`. `featured` rows for that channel that are no longer in the list are **deleted**: a channel no longer featured is no longer this source's candidate. `manual` rows are never touched. Then it sets `featured_checked_at = now()`.
   - An empty list is valid. It clears the `featured` rows and still sets `featured_checked_at`.
6. **Gateway.** `/worker/featured-due` and `/worker/commit-featured` beside the existing discover routes in `worker-gateway.ts`, with the same lease checks and SQLSTATE mapping. Contract: `FeaturedCandidatesCommitSchema` in `packages/contracts/src/competitors.ts` (zod, `.strict()`). Claude signs off on this contract by issuing this work order.
7. **Runner.** In the YouTube discover path, after `commit_catalogue` and the channel-profile commit (WO-21), call `featured_due`. If due, fetch and commit.
   - A fetch or commit failure makes the discover finish **`partial`** with `featured_channels_failed`, never `succeeded` (invariant 2). Videos and the profile already committed stay.
   - A `quota_exceeded` from YouTube keeps its existing handling.
   - Nothing is fetched when not due.

## Acceptance criteria
- [ ] Each new test fails on the old code (say how you proved it)
- [ ] Manual add, list and remove work. Each refusal case holds, viewer and non-member included, and workspace A never reads or writes B's candidates.
- [ ] Featured commit:
  - the whole batch is refused for each malformed case (bad id, self, duplicate, over-long title, over 100);
  - replay is a no-op and a conflicting replay is `batch_conflict`;
  - a channel that drops out of the featured list loses its `featured` row and keeps its `manual` one;
  - an empty list clears the `featured` rows and sets `featured_checked_at`.
- [ ] `featured-due` is true when `featured_checked_at` is null or 8 days old, false when it is 6 days old, and false for a non-YouTube channel
- [ ] Python, with every HTTP call mocked:
  - 0 calls when not due;
  - 2 calls for ≤50 featured ids and 3 for 51–100;
  - the channel itself is dropped and duplicates are merged;
  - a failure gives a `partial` discover with `featured_channels_failed`;
  - `golden_featured.json` is written by the real builder, and the TS seam test commits it through PGlite.
